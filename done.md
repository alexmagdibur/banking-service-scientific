## Этап 4. Идемпотентность и чтение переводов — выполнен

**Изменено / создано** (пакет `com.example.bankigservicescientific.transfer`, `error`):
- `TransferService.transfer` (по-прежнему публичный `@Transactional`) теперь возвращает `TransferResult(transfer, created)`. Порядок: валидация → `pg_advisory_xact_lock(hashtextextended(ключ, 0))` (запросы с одним ключом выстраиваются в очередь) → поиск перевода по ключу → при совпадении отпечатка возвращается сохранённый перевод без изменения балансов, при несовпадении — `IdempotencyConflictException` → иначе блокировка счетов, проверки, списание/зачисление, вставка. Ограничение UNIQUE на `idempotency_key` оставлено как последний рубеж (его срабатывание даёт 409 и пишется в лог).
- `TransferService.get` / `latest` — чтение (`@Transactional(readOnly = true)`).
- `TransferRepository` — `findByIdempotencyKey`, `findById`, `findLatest(limit)` (порядок `created_at DESC, id DESC`), `lockIdempotencyKey`.
- `TransferController` — `POST` отвечает 201 (новый) или 200 (повтор); `GET /api/transfers/{id}`; `GET /api/transfers?limit=` (по умолчанию 20, допустимо 1..100, иначе 400; пустое `limit=` трактуется Spring как отсутствующий параметр).
- Новые исключения `IdempotencyConflictException` (409 `IDEMPOTENCY_KEY_CONFLICT`), `TransferNotFoundException` (404 `TRANSFER_NOT_FOUND`) и их обработчики. Неверный UUID в пути → 400.
- Тесты: `IdempotencyAndReadApiTests` (9), `TransferRollbackTests` (1: `@MockitoSpyBean` заставляет INSERT перевода падать уже после списания/зачисления; проверено в БД, что балансы и число переводов не изменились). Из `TransferApiTests` убран прежний тест отката, основанный на повторе ключа (теперь повтор даёт 409 до списания).

**Проверка** (временный кластер PostgreSQL 18.4, порт 55432, затем удалён):

- Endpoint предназначен для вызова через `kubectl port-forward` к конкретному Pod и не входит в публичный Service; настройка Kubernetes (порт 8081 только внутри кластера, профиль `research` только в исследовательских Deployment) — этапы 11–12. Защиты аутентификацией нет (по ТЗ — изолированный стенд).
- Если во время нарушения у Pod настроена liveness-проба, Kubernetes может перезапустить контейнер раньше, чем окончится окно — это и есть изучаемое поведение; в этапе 9 это не проверялось (нет Kubernetes).
- Проверка выполнена на временной БД; на БД пользователя (порт 5432) этап не запускался.

### Этап 11: подтверждение пользователя на Ubuntu Server (дополнение)

По сообщению пользователя, стенд развёрнут на **Ubuntu Server в виртуальной машине (VMware/VirtualBox) на ноутбуке** и «всё работает»: K3s установлен, образ доставлен (`docker save` → `scp` → `sudo k3s ctr images import`), манифесты `k8s/base` применены (`sudo k3s kubectl apply -k`), поды `postgres-0` и `bank-api` дошли до `Running`, приложение доступно с основного компьютера через NodePort 30080, переводы и сохранность данных проверены пользователем. Скриншоты/вывод этих проверок в этой сессии не приводились, поэтому подтверждение принято со слов пользователя.

Что выяснилось при развёртывании (учесть в README этапа 14):
- На ВМ изначально был установлен **MicroK8s** (процесс `kubelite` занимал порт 10250), из-за чего K3s падал с `bind: address already in use`; два Kubernetes на одной машине несовместимы — MicroK8s нужно остановить или удалить (`sudo snap remove microk8s --purge`).
- Сразу после установки K3s `kubectl` отвечает `No resources found` / `connection refused` / `unable to handle the request` 1–2 минуты — это нормально, нужно дождаться `Ready`.
- ВМ в режиме NAT получает адрес внутренней сети гипервизора (192.168.197.x), недоступный с основного ПК (192.168.31.x); нужен режим **Bridged** (или проброс портов). В командах `<ip>` пишется без угловых скобок.
- Сравнение результатов исследования должно учитывать, что стенд — ВМ на ноутбуке: ресурсы делятся с хостовой ОС, сеть ПК→ноутбук входит в измеряемую задержку (записать в ограничения стенда).
