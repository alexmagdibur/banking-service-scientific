# Поэтапная разработка учебного Bank API

Документ для последовательной работы в Claude Code или Codex. Полные требования находятся в `E:/techprog/bankig-service-scientific/BANKING_API_RESEARCH_SPEC.md`. Рабочий проект — `E:/techprog/bankig-service-scientific` (написание `bankig` в имени каталога сохранено намеренно). Этот план делит ТЗ на небольшие задания; при расхождении деталей приоритет у полного ТЗ.

## Как выполнять этапы

1. Перед первым этапом дать исполнителю путь к полному ТЗ и этому плану. Работать в существующем проекте, не создавать новый Spring-проект.
2. За один заход поручать **один этап**. Исполнитель может читать полный ТЗ, но не должен заранее реализовывать следующие этапы.
3. В конце каждого этапа исполнитель сообщает: изменённые файлы, выполненные команды и результаты, оставшиеся ограничения. Непроверенное не называть готовым.
4. Если для проверки нужны PostgreSQL, Docker, K3s или k6, которых нет в текущей среде, завершить доступную часть, записать точную команду для проверки и не переходить к зависимому этапу, пока ключевое условие не проверено.
5. Сохранять существующие изменения пользователя. Использовать текущие Java 17, Spring Boot 4.1.2 и Maven Wrapper, если проверка проекта не выявит иного.
6. Не добавлять реальные платежи, авторизацию, отдельный фронтенд-сервер, Kafka, Redis или другие функции вне ТЗ.

## Этап 0. Проверка исходного проекта

**Задача.** Осмотреть `pom.xml`, пакет Java, конфигурацию, структуру каталогов, статус Git и возможность сборки. Зафиксировать найденные версии и любые препятствия. Пока не писать бизнес-код.

**Результат.** Краткий список исходных файлов и зависимостей; успешная базовая сборка либо точная причина, почему она не прошла.

**Проверка.** Запустить Maven Wrapper с тестами, доступными в исходном проекте. Не менять версии «на всякий случай».

## Этап 1. Подключение PostgreSQL и схема

**Задача.** Добавить конфигурацию БД через `BANK_DB_URL`, `BANK_DB_USER`, `BANK_DB_PASSWORD`; подключить Flyway; создать таблицы `accounts` и `transfers` с ограничениями из ТЗ. Одной миграцией внести три тестовых счёта. Подготовить `.env.example` без паролей и `scripts/reset-test-data.sql`, который запускается только вручную.

**Результат.** Пустая тестовая БД после запуска получает схему и три счёта с начальным балансом. Повторный запуск не сбрасывает данные.

**Проверка.** Запустить приложение с тестовой PostgreSQL, проверить таблицы и суммы, перезапустить приложение и убедиться, что миграция не выполняет повторное пополнение.

## Этап 2. Чтение счетов и единый формат ошибок

**Задача.** Сделать `GET /api/accounts` и `GET /api/accounts/{id}`. Возвращать счета по возрастанию ID. Добавить общий формат ошибок `{code, message, timestamp}` без stack trace и SQL в HTTP-ответе.

**Результат.** API показывает тестовые счета; неизвестный ID даёт 404.

**Проверка.** Проверить ответы для существующего и отсутствующего счёта; запустить сборку и доступные тесты.

## Этап 3. Транзакционный перевод

**Задача.** Сделать `POST /api/transfers` с проверкой суммы, существования и различия счетов, достаточности средств. Деньги хранить целыми копейками. Списание, зачисление и запись перевода выполнять в одной транзакции. Блокировать строки счетов в постоянном порядке по ID.

**Граница этапа.** Пока можно реализовать базовый успешный перевод; полную обработку повторов по `Idempotency-Key` завершить на этапе 4. Уже здесь предусмотреть поле ключа в данных и его обязательность по контракту API.

**Результат.** Корректный перевод меняет два баланса на одинаковую сумму и сохраняет запись; ошибочный не меняет состояние.

**Проверка.** Проверить удачный перевод, недостаток средств, перевод самому себе, нулевую/отрицательную сумму, неизвестный счёт и сумму выше рабочего лимита. После каждой ошибки сверить оба баланса и число переводов.

## Этап 4. Идемпотентность и чтение переводов

**Задача.** Завершить поддержку `Idempotency-Key`: первый запрос создаёт перевод с 201, точный повтор возвращает тот же перевод с 200, тот же ключ с другим содержимым даёт 409. Обеспечить корректное поведение при одновременном использовании одного ключа. Сделать `GET /api/transfers/{id}` и `GET /api/transfers?limit=20`.

**Результат.** Повтор запроса никогда не создаёт второе списание. Историю и конкретный перевод можно прочитать через API.

**Проверка.** Отправить одинаковый POST дважды и сравнить ID/балансы; повторить ключ с другой суммой; проверить ограничение `limit` и 404 для неизвестного перевода.

## Этап 5. Интеграционные тесты банковских инвариантов

**Задача.** Добавить содержательные тесты с отдельной тестовой PostgreSQL. Покрыть атомарность перевода, откат при ошибке, неизменность общей суммы, отсутствие отрицательных балансов, точный и конфликтующий повтор ключа, одновременные переводы и одновременный повтор одного ключа.

**Результат.** Тесты проверяют фактическое состояние БД и HTTP-ответы, а не только вызовы моков.

**Проверка.** Запустить тесты несколько раз. Если тестовая PostgreSQL недоступна, не объявлять этап завершённым только по компиляции тестов. Этот этап — обязательные ворота перед интерфейсом и экспериментальной частью.

## Этап 6. Простая страница в браузере

**Задача.** Создать `index.html`, `styles.css`, `app.js` в `src/main/resources/static`. Показать счета, форму перевода и последние 20 переводов. Переводить ввод рублей в целые копейки без `float`-арифметики при формировании суммы. Создавать новый ключ для нового перевода и сохранять его для безопасного повтора после неопределённого ответа. Показывать ошибки и кнопку проверки результата.

**Результат.** Через браузер можно увидеть балансы, сделать перевод и увидеть историю. Страница остаётся минимальной и работает без Node.js и фронтенд-фреймворка.

**Проверка.** Вручную открыть `/`, выполнить перевод, обновить страницу, проверить сохранность данных и поведение при ошибке API/тайм-ауте.

## Этап 7. Проверки состояния экземпляра

**Задача.** Настроить Actuator, основной порт 8080 и внутренний порт управления 8081. Обеспечить `/livez` и `/readyz` на основном порту. Определить и описать роль PostgreSQL в readiness; liveness не должен зависеть от БД. Добавить идентификатор экземпляра в лог и, при необходимости, заголовок `X-Instance-Id`.

**Результат.** Оркестратор может проверять тот же HTTP-сервер, который обслуживает клиентов; экземпляры различимы.

**Проверка.** Проверить оба пути на 8080 в нормальном состоянии и при временной недоступности тестовой БД.

## Этап 8. Метрики и журналы

**Задача.** Добавить Prometheus registry, стандартные HTTP/JVM/процессные метрики и ограниченные по числу меток бизнес-метрики просмотров баланса и переводов. Настроить журналирование времени UTC, типа операции, ID экземпляра, исхода и длительности. Не логировать секреты и полные ключи идемпотентности.

**Результат.** `/actuator/prometheus` доступен на внутреннем порту; метрики и логи помогают объяснять поведение Pod. Итоговые научные показатели `R` и `K` внутри приложения не вычисляются.

**Проверка.** Сделать успешный запрос и запрос с бизнес-ошибкой, проверить метрики/логи и убедиться, что в них нет ID счетов и переводов в качестве Prometheus-меток.

## Этап 9. Управляемая недоступность для исследования

**Задача.** Только в профиле `research` добавить адресное включение режима `UNRESPONSIVE` для одного экземпляра через внутренний управляющий endpoint, согласно ТЗ. Ограничить длительность 1–120 секундами, автоматически выключать режим, переводить readiness/liveness в неуспешное состояние. Обычный запуск не должен открывать этот endpoint.

**Результат.** Можно воспроизводимо моделировать недоступность выбранного Pod без изменения банковских данных.

**Проверка.** Проверить обычный профиль, включение режима, состояние пользовательского API и probes во время нарушения, автоматическое снятие и восстановление. Не называть моделируемую недоступность настоящим отказом узла.

## Этап 10. Контейнерный образ

**Задача.** Написать Dockerfile с воспроизводимой сборкой через Maven Wrapper и запуском JAR. Не включать в образ локальные секреты. Документировать переменные БД.

**Результат.** Один образ приложения работает с внешней PostgreSQL и может использоваться во всех вариантах Kubernetes.

**Проверка.** Собрать образ, запустить его с тестовой БД, проверить `/api/accounts`, `/livez`, `/readyz`. Если Docker недоступен в среде исполнителя, записать непроверенную команду и результат доступной проверки сборки JAR.

## Этап 11. Базовый запуск на Ubuntu/K3s

**Задача.** Подготовить манифесты PostgreSQL с постоянным томом, Secret/ConfigMap для тестовых параметров, Deployment и Service для `bank-api`. Выбрать простой путь доставки образа в K3s и записать его в README. Обеспечить доступ к API с основного компьютера в локальной сети.

**Результат.** На Ubuntu Server можно развернуть БД и приложение, открыть страницу и выполнить перевод. Перезапуск Pod не удаляет данные.

**Проверка.** Проверить состояние Pod, доступность API с другого компьютера, перевод и сохранение данных после перезапуска Pod. Отказ физического узла этим этапом не проверяется.

## Этап 12. Варианты Kubernetes V0–V3

**Задача.** Подготовить четыре небольших варианта манифестов: V0 — 1 реплика; V1 — 3 реплики; V2 — 3 реплики с probes; V3 — 3–5 реплик с probes и HPA по CPU. Во всех вариантах оставить один образ, одну БД и одинаковые requests/limits. Не менять Java-код между вариантами.

**Результат.** Вариант выбирается применением конфигурации, а не правкой приложения. V1 позволяет отдельно оценить влияние числа реплик.

**Проверка.** Последовательно применить каждый вариант и проверить число Pod, маршрутизацию, probes. Для V3 проверить наличие метрик CPU и возможность создания дополнительных Pod; без этого HPA не считать проверенным.

## Этап 13. Сценарии k6

**Задача.** Создать `load/smoke.js`, `constant.js`, `spike.js`. Сделать настраиваемыми адрес, длительность, частоту, клиентский тайм-аут и долю чтений/переводов. Проверять содержимое ответов, уникальность ключей для новых переводов и безопасный повтор после неопределённого ответа. Исключить быстрое опустошение одного счёта.

**Результат.** Есть воспроизводимые клиентские сценарии для проверки API, постоянной нагрузки и всплеска. Клиентские тайм-ауты видны отдельно от HTTP-ошибок.

**Проверка.** Запустить smoke на работающем стенде, затем короткие constant/spike; после серии проверить общую сумму балансов и отсутствие дублей ключей. Пока не делать научных выводов из одного прогона.

## Этап 14. Сквозная проверка и документация

**Задача.** Свести README в точную инструкцию: локальный запуск Windows, создание тестовой БД, ручной сброс данных, сборка образа, запуск K3s, доступ из браузера, выбор V0–V3, запуск k6, расположение метрик и ограничения стенда. Выполнить доступные проверки всей цепочки и исправить обнаруженные ошибки.

**Результат.** Другой человек может развернуть стенд по README, не угадывая команды и имена файлов. Данные и сырые результаты можно сохранить для будущего анализа.

**Проверка.** Повторить инструкции на доступной среде; отметить фактически пройденные проверки и то, что требует ноутбука с Ubuntu/K3s. Не вписывать вымышленные экспериментальные результаты.
