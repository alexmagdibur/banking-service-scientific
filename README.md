# Research Bank API

Тестовое банковское веб-приложение для исследования отказоустойчивости в Kubernetes. Оно показывает три вымышленных счёта, выполняет переводы между ними и позволяет измерять результат клиентских операций при удалении Pod, временной недоступности экземпляра и всплеске нагрузки. Реальные деньги и персональные данные не используются.

Приложение написано на Java 17 и Spring Boot 4.1.2. Простая страница на HTML, CSS и JavaScript открывается в браузере; тот же сервер предоставляет REST API. Единственное постоянное хранилище — PostgreSQL: данные счетов и переводов не привязаны к экземпляру Bank API. Один и тот же образ `bank-api:dev` используется для всех вариантов стенда.

## Возможности и устройство

- Просмотр счетов, отправка перевода и просмотр истории через страницу `/` или REST API.
- Суммы хранятся целым числом копеек. Списание, зачисление и запись перевода выполняются в одной транзакции PostgreSQL.
- Заголовок `Idempotency-Key` связывает повтор запроса с тем же переводом. Первый успешный запрос возвращает `201`, повтор с тем же ключом и реквизитами — `200` и прежний результат.
- Если браузер не получил однозначного ответа, он сохраняет ключ попытки локально и предлагает проверить результат. Повторная отправка использует тот же ключ.
- Flyway создаёт схему и три тестовых счёта при первом запуске. Перезапуск приложения не сбрасывает данные.
- `/livez` проверяет состояние экземпляра, `/readyz` дополнительно учитывает доступность БД. Метрики Prometheus доступны через отдельный служебный порт.

Три исходных счёта имеют ID `1001`, `1002`, `1003` и баланс по `10 000 000` копеек. PostgreSQL в экспериментальном стенде один: исследование не проверяет отказ самой базы данных или физического узла.

## Запуск для разработки на Windows

Нужны JDK 17 или новее, PostgreSQL и Maven Wrapper из репозитория; устанавливать Maven отдельно не требуется. Создайте пустую БД `bank_test` и пользователя с правами на неё. БД должна существовать до запуска приложения; таблицы и счета создаст Flyway.

В PowerShell из корня проекта задайте параметры подключения и запустите сервис:

```powershell
$env:BANK_DB_URL = 'jdbc:postgresql://localhost:5432/bank_test'
$env:BANK_DB_USER = 'bank'
$env:BANK_DB_PASSWORD = 'пароль-вашей-тестовой-БД'
.\mvnw.cmd spring-boot:run
```

Откройте <http://localhost:8080/>. Если порт 8080 занят, перед запуском задайте, например, `$env:SERVER_PORT = '8090'` и откройте порт 8090. Файл `.env.example` перечисляет переменные, но Maven и IntelliJ IDEA не загружают `.env` автоматически: добавьте их в конфигурацию запуска или окружение процесса.

Проверка приложения:

```powershell
Invoke-RestMethod http://localhost:8080/api/accounts
Invoke-RestMethod http://localhost:8080/livez
Invoke-RestMethod http://localhost:8080/readyz
```

### Запуск приложения в Docker

Сначала соберите образ:

```powershell
docker build -t bank-api:dev .
```

Если PostgreSQL работает на компьютере с Docker Desktop, создайте локальный `.env` на основе `.env.example`, укажите пароль и адрес `jdbc:postgresql://host.docker.internal:5432/bank_test`, затем запустите контейнер:

```powershell
docker run --rm --env-file .env -p 8080:8080 bank-api:dev
```

PostgreSQL должен принимать соединения из контейнера. Порт управления `8081` публиковать для обычного использования не нужно. В образе нет пароля БД, а `.env` исключён из Git и контекста сборки.

## HTTP API

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/accounts` | Все тестовые счета |
| `GET /api/accounts/{id}` | Один счёт и его баланс в копейках |
| `POST /api/transfers` | Перевод; обязателен заголовок `Idempotency-Key` |
| `GET /api/transfers?limit=20` | Последние переводы; `limit` от 1 до 100 |
| `GET /api/transfers/{id}` | Перевод по UUID |
| `GET /livez`, `GET /readyz` | Проверки состояния на пользовательском порту |

Пример перевода 100 копеек из счёта `1001` в счёт `1002`:

```powershell
Invoke-RestMethod -Method Post http://localhost:8080/api/transfers `
  -ContentType 'application/json' `
  -Headers @{ 'Idempotency-Key' = 'readme-demo-001' } `
  -Body '{"fromAccountId":1001,"toAccountId":1002,"amountMinor":100}'
```

Для нового перевода используйте новый ключ. Повтор того же запроса с прежним ключом возвращает уже записанный перевод. Метрики находятся на `http://localhost:8081/actuator/prometheus` при локальном запуске; в Kubernetes этот порт не включён в пользовательский Service.

## Стенд Kubernetes

Манифесты рассчитаны на одноузловой K3s в Ubuntu VM; генератор k6 запускается в Windows на том же физическом компьютере. В K3s должны быть доступны образы `bank-api:dev` и `postgres:18`. Базовые ресурсы находятся в `k8s/base/`: namespace `bank`, тестовый Secret, PostgreSQL в StatefulSet с PVC и Bank API через NodePort `30080`. `k8s/variants/` добавляет исследовательский профиль и настройки вариантов. Секрет в репозитории содержит только учётные данные изолированного тестового стенда.

Соберите образ на компьютере и импортируйте его в containerd на Ubuntu VM: наличие образа в Docker на Windows само по себе не делает его доступным для K3s.

```powershell
docker build -t bank-api:dev .
docker save bank-api:dev -o bank-api.tar
scp bank-api.tar user@VM_IP:~/bank-api.tar
```

Скопируйте на VM каталоги `k8s/` и `scripts/`. На VM выполните:

```bash
sudo k3s ctr images import ~/bank-api.tar
sudo k3s kubectl apply -k k8s/variants/v0
sudo k3s kubectl -n bank get pods
```

После готовности Pod страница доступна по `http://VM_IP:30080/`. Для доступа к служебному порту конкретного Pod используйте `kubectl port-forward`; NodePort открывает только порт API. Для переключения варианта при настроенном пользовательском `~/.kube/config`:

```bash
bash scripts/switch-variant.sh v2
k3s kubectl -n bank get pods,hpa
```

| Вариант | Bank API | Проверки состояния | HPA |
| --- | ---: | --- | --- |
| V0 | 1 реплика | нет | нет |
| V1 | 3 реплики | нет | нет |
| V2 | 3 реплики | startup, readiness, liveness | нет |
| V3 | 3–5 реплик | как в V2 | цель CPU 30 % от запроса 250m |

Переключатель удаляет HPA прежнего варианта и ждёт завершения обновления Deployment. Данные PostgreSQL сохраняются при замене Pod. Удаление namespace вместе с PVC удаляет тестовые данные.

## Нагрузочные прогоны и данные исследования

Сценарии k6 лежат в `load/`. Каждая итерация выполняет одну операцию: четыре из пяти — чтение баланса, пятая — перевод 100 копеек с уникальным ключом. Клиентский тайм-аут в основных сценариях — 3 с.

| Сценарий | Нагрузка в течение 300 с | Воздействие |
| --- | --- | --- |
| Удаление Pod | 20 операций/с | Удаление одного Pod примерно на 120-й секунде |
| Недоступность экземпляра | 20 операций/с | `UNRESPONSIVE` на выбранном Pod с 120-й секунды на 60 с |
| Всплеск | 15 / 40 / 15 операций/с по фазам 120 / 60 / 120 с | Повышение частоты в средней фазе |

Исследовательский endpoint включается только при `SPRING_PROFILES_ACTIVE=research` и доступен на служебном порту выбранного Pod. Он предназначен для тестового стенда, не для обычного запуска.

Для короткой проверки генератора на Windows с Docker Desktop замените `VM_IP` адресом VM и выполните в корне проекта:

```powershell
$project = (Get-Location).Path
$runId = 'pilot_' + [DateTime]::UtcNow.ToString('yyyyMMddTHHmmssZ')
New-Item -ItemType Directory -Force -Path (Join-Path $project "results\$runId") | Out-Null
docker run --rm `
  --mount "type=bind,source=$project\load,target=/scripts,readonly" `
  --mount "type=bind,source=$project\results,target=/results" `
  -e BASE_URL=http://VM_IP:30080 -e RUN_ID=$runId `
  -e RATE=2 -e DURATION_SECONDS=10 `
  grafana/k6@sha256:e66db15b860113878fa74670e31f5e274830b7b6e42c8bff28b2f2d86a257603 `
  run --out "json=/results/$runId/raw.json" `
  --summary-export "/results/$runId/summary.json" /scripts/constant.js
```

Основной прогон требует синхронизированного воздействия, сбора событий и CPU Pod, проверки часов и сброса тестовых данных между повторами. Порядок проведения, критерии зачёта и формулы приведены в [experimental_data.md](experimental_data.md). Скрипты `scripts/run-main-*.ps1` автоматизируют прогоны, но содержат пути, адрес VM и путь к SSH-ключу конкретного стенда: перед повторным использованием их нужно адаптировать. `scripts/analyze-experiment-run.mjs` рассчитывает показатели по полной папке прогона с `raw.json`, `summary.json`, отметками часов и выборками ресурсов.

Проведены четыре повтора каждой пары «три сценария × четыре варианта», всего **48 зачтённых прогонов**. Сводки по прогонам находятся в [experimental_run_summary_48.csv](experimental_run_summary_48.csv) и [experimental_transfer_reconciliation_48.csv](experimental_transfer_reconciliation_48.csv); исходные файлы — в локальном `results/` (не входят в Git). В исследовании сравниваются доля успешных операций `A`, время восстановления `Trec`, 95-й процентиль задержки успешного чтения `L95` и составная оценка `R`. При исследованном всплеске HPA не увеличил число реплик, поэтому эти данные не измеряют эффект сработавшего масштабирования.

## Тесты и сброс данных

Интеграционные тесты работают с настоящей PostgreSQL и перед каждым тестом очищают переводы и восстанавливают балансы. Используйте отдельную БД, имя которой оканчивается на `_test`:

```powershell
$env:BANK_TEST_DB_URL = 'jdbc:postgresql://localhost:5432/bank_test'
$env:BANK_TEST_DB_USER = 'bank'
$env:BANK_TEST_DB_PASSWORD = 'пароль-тестовой-БД'
.\mvnw.cmd test
```

Миграция Flyway не обнуляет данные при перезапуске. Для ручного сброса **только тестовой БД** используйте `scripts/reset-test-data.sql`; он удаляет переводы и возвращает каждому из трёх счетов баланс `10 000 000` копеек.
