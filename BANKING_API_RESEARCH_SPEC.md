# Техническое задание: учебный Bank API для исследования отказоустойчивости в Kubernetes

Версия ТЗ: 1.0, 23.10.2026. Документ предназначен для передачи Codex или Claude Code как задания на реализацию.

## 1. Исходный проект и цель

Работать в существующем проекте E:/techprog/bankig-service-scientific. Каталог действительно называется bankig-service-scientific; это не повод создавать второй проект или переименовывать исходный каталог. В текущем pom.xml: Spring Boot 4.1.2, Maven Wrapper, целевая Java 17, groupId com.example, artifactId banking-service-scientific, базовый пакет com.example.bankigservicescientific. Уже подключены Web MVC, Data JDBC, Validation, Actuator и драйвер PostgreSQL. Перед изменениями повторно проверить фактическое состояние проекта и сохранить существующие изменения пользователя.

Цель — небольшой воспроизводимый стенд, на котором можно оценивать пользовательскую доступность, время восстановления, задержку и расход ресурсов при разных настройках Kubernetes. Это модель нескольких типичных банковских операций с тестовыми счетами, а не программное обеспечение реального банка. В приложении нет настоящих денег и персональных данных.

Обязательное правило: состояние счетов и переводов хранится только в PostgreSQL. Экземпляры Java-приложения взаимозаменяемы и не хранят бизнес-состояние в памяти. Измерения проводятся по сквозным пользовательским операциям. Научные показатели R и K из черновика статьи вычисляются при обработке результатов отдельно; не встраивать их расчёт в Bank API.

## 2. Границы первой версии

Реализовать один Java-сервис bank-api, одну базу PostgreSQL и одну статическую страницу, которую отдаёт тот же Java-сервис. Не создавать отдельный сервер фронтенда.

Функции: просмотр тестовых счетов и балансов, перевод между счетами, просмотр последних переводов и проверка состояния конкретного перевода. Нужны понятные ошибки и корректное восстановление после перезапуска контейнера.

Не добавлять регистрацию, авторизацию, роли, реальные платёжные шлюзы, Kafka, Redis, email, уведомления, микросервисное разбиение, React/Vue/Angular, сложные анимации, диаграммы на пользовательской странице или панель управления Kubernetes. Не добавлять искусственные «банковские» функции, которые не участвуют в исследовании. Обоснованное расширение обсуждать отдельно после работающей базовой версии.

## 3. Архитектура

Браузер и внешний генератор нагрузки обращаются к одному HTTP API через Kubernetes Service. Service направляет запросы к одному или нескольким Pod с bank-api. Каждый Pod подключается к одной PostgreSQL. Статические файлы страницы лежат в src/main/resources/static и доступны по корневому URL. В локальном режиме та же программа подключается к установленному у пользователя PostgreSQL.

Логическая схема:

    Браузер / k6
           |
           v
    Kubernetes Service -> bank-api (1..N одинаковых Pod)
                                |
                                v
                           PostgreSQL

PostgreSQL остаётся одинаково настроенным во всех вариантах исследования. Отказ базы данных, узла Kubernetes и сетевого оборудования не входит в базовый предмет исследования. Не делать выводов об отказоустойчивости всей банковской инфраструктуры на основании устойчивости одного прикладного сервиса.

## 4. Модель данных и банковские инварианты

Денежные суммы хранить целыми числами в копейках, тип Java long и PostgreSQL BIGINT; не использовать float/double для денег. UI показывает рубли с двумя знаками после запятой. Все даты и время хранить в UTC.

Минимальные таблицы:

- accounts: id BIGINT PRIMARY KEY; display_name VARCHAR(100) NOT NULL; balance_minor BIGINT NOT NULL с CHECK(balance_minor >= 0).
- transfers: id UUID PRIMARY KEY; idempotency_key VARCHAR(128) NOT NULL UNIQUE; from_account_id и to_account_id как внешние ключи accounts; amount_minor BIGINT NOT NULL с CHECK(amount_minor > 0); request_fingerprint VARCHAR(64) NOT NULL; status VARCHAR(20) NOT NULL; created_at TIMESTAMPTZ NOT NULL. Ограничить from_account_id <> to_account_id. Для первой версии допустим только конечный статус COMPLETED: не оставлять после коммита запись «в процессе».

Создать миграцию схемы через Flyway. Для Spring Boot 4 с PostgreSQL при необходимости добавить spring-boot-starter-flyway и flyway-database-postgresql. Использовать только один механизм создания схемы: не смешивать Flyway с автоматическим schema.sql/data.sql на каждом запуске.

Начальные данные строго тестовые: три счёта с ID 1001, 1002, 1003, названиями «Счёт А», «Счёт Б», «Счёт В» и балансом по 10 000 000 копеек (100 000 рублей). Заполнять их один раз при создании БД. Перезапуск приложения и Pod не должен сбрасывать деньги и историю. Подготовить отдельный явный скрипт scripts/reset-test-data.sql, который в одной транзакции удаляет переводы и возвращает исходные балансы. Этот скрипт не должен выполняться автоматически при старте приложения.

Для каждого успешного перевода одновременно выполняются четыре условия: сумма списана у отправителя один раз; получателю зачислена та же сумма один раз; запись перевода сохранена; суммарный баланс всех счетов не изменился. Недостаток средств, неверный счёт, неположительная сумма и перевод самому себе не меняют состояние. При одновременных переводах нельзя получить отрицательный баланс или потерять обновление.

Реализовать перевод как одну транзакцию PostgreSQL. Блокировать две строки счетов в постоянном порядке по ID (например, SELECT ... FOR UPDATE) и учитывать конкурентные запросы. Проверить, что транзакционная аннотация действительно применяется к публичному методу сервиса. Не ограничиваться проверкой баланса вне транзакции. Ошибка после частичного выполнения должна приводить к откату всех изменений.

## 5. Идемпотентность перевода

Клиент обязан прислать заголовок Idempotency-Key с непрозрачным уникальным значением длиной 1..128 символов. Ключ создаёт клиент и повторно использует только при повторе того же перевода. Сервер сохраняет ключ и отпечаток нормализованных полей запроса.

Первый успешный запрос с ключом создаёт перевод и отвечает HTTP 201. Повтор с тем же ключом и точно теми же полями возвращает тот же ID, статус и данные перевода с HTTP 200, не выполняя второе списание. Тот же ключ с иными полями даёт HTTP 409 без изменения данных. Одновременные запросы с одним ключом также создают не более одного перевода; обеспечить это ограничением UNIQUE и корректной логикой транзакции. Если процесс завершился до коммита, повтор может выполнить перевод; если после коммита, повтор возвращает сохранённый результат. Проверить оба случая на уровне БД и API, насколько позволяет тестовый стенд.

## 6. HTTP API

Базовый префикс /api. JSON в UTF-8. Ответы об ошибках должны иметь единый простой вид: code, message, timestamp. Не включать stack trace и SQL в пользовательский ответ.

- GET /api/accounts — HTTP 200, массив объектов {id, displayName, balanceMinor}. Порядок по id.
- GET /api/accounts/{id} — HTTP 200 с одним счётом; HTTP 404, если ID отсутствует.
- POST /api/transfers — тело {fromAccountId, toAccountId, amountMinor}, обязательный заголовок Idempotency-Key; HTTP 201 для нового перевода, HTTP 200 для корректного повтора. Ответ {id, fromAccountId, toAccountId, amountMinor, status, createdAt}.
- GET /api/transfers/{id} — HTTP 200 с переводом либо HTTP 404.
- GET /api/transfers?limit=20 — HTTP 200, последние переводы в обратном порядке по createdAt и id; limit от 1 до 100, по умолчанию 20.

Правила ошибок: HTTP 400 — неверный формат, отсутствующий ключ или недопустимая сумма; HTTP 404 — неизвестный счёт/перевод; HTTP 409 — недостаток средств или конфликт ключа идемпотентности; HTTP 503 — недоступна необходимая зависимость, если это можно определить; HTTP 500 — прочая непредвиденная серверная ошибка. Не выдавать 200 при нарушенном банковском инварианте.

Для POST сумма минимум 1 копейка, максимум 1 000 000 копеек в одной операции (рабочее ограничение учебного стенда), отправитель и получатель различаются. Применить Bean Validation к входному DTO. Список счетов и история доступны без авторизации только потому, что используются вымышленные данные в изолированном учебном стенде.

## 7. Минимальный интерфейс в браузере

Одна страница /, три обычных блока:

1. Таблица тестовых счетов: ID, название, баланс в рублях. Кнопка «Обновить».
2. Форма перевода: счёт отправителя, счёт получателя, сумма в рублях, кнопка «Перевести». JavaScript переводит ввод в целые копейки без ошибок округления и создаёт Idempotency-Key для каждого нового намерения перевода. При ручном повторе того же запроса после неопределённого ответа использовать прежний ключ.
3. Таблица последних 20 переводов: время, откуда, куда, сумма, статус. После успешного перевода обновить баланс и историю.

Показывать понятное сообщение при 400/404/409/503 и тайм-ауте. В случае тайм-аута перевода не писать без проверки «перевод не выполнен»: результат может быть неизвестен клиенту. Предусмотреть кнопку «Проверить результат», использующую сохранённый ключ/ID и данные из API; если ID не получен, повтор POST с тем же Idempotency-Key безопасен. Не хранить баланс только в браузере как источник истины.

Реализация: index.html, styles.css, app.js без сборщика JavaScript и без стороннего фронтенд-фреймворка. Аккуратная, читаемая, но простая вёрстка. Не добавлять логин, графики, имитацию мобильного банка и визуальные эффекты. Фронтенд нужен для ручной проверки; нагрузка для исследования подаётся напрямую в тот же API.

## 8. Проверки состояния и управляемые нарушения

Обычный режим: Spring Boot Actuator. У приложения основной HTTP-порт 8080; отдельный внутренний порт управления 8081 допустим для метрик и тестового управляющего endpoint. Если порт управления отдельный, включить management.endpoint.health.probes.add-additional-paths=true и направить Kubernetes liveness/readiness на /livez и /readyz основного порта 8080, чтобы проверки использовали тот же HTTP-сервер, что и пользовательские запросы. Liveness не должен зависеть от PostgreSQL. Readiness показывает, может ли экземпляр принимать запросы; решение о включении проверки БД в readiness явно описать и одинаково применять во всех вариантах.

В профиле research реализовать минимальный способ адресно ввести нарушение в выбранный Pod. Предпочтительный контракт: управляющий POST /actuator/researchfault на порту 8081, вызываемый только через port-forward к конкретному Pod, с параметрами mode=UNRESPONSIVE и durationSeconds от 1 до 120. Этот endpoint не должен входить в публичный Kubernetes Service или пользовательский фронтенд. Он возвращает подтверждение и ID экземпляра до включения нарушения. Режим UNRESPONSIVE временно делает бизнес-запросы данного Pod неспособными завершиться в клиентский тайм-аут и переводит его readiness/liveness в неуспешное состояние. По истечении durationSeconds состояние автоматически снимается; при перезапуске Pod также исчезает. Назвать это в документации «моделируемая недоступность экземпляра», а не настоящая взаимная блокировка потоков. Реализовать так, чтобы само управление и логирование события оставались доступны до перезапуска.

Профиль research не активировать в обычном локальном запуске по умолчанию. Удаление Pod выполняется средствами Kubernetes извне приложения. Всплеск нагрузки создаётся внешним генератором; не реализовывать кнопку «сломать приложение» в браузере и не генерировать нагрузку внутри bank-api.

У каждого экземпляра должен быть понятный идентификатор (например, hostname/Pod name), записываемый в логах и необязательном ответном заголовке X-Instance-Id. Не использовать ID счёта или перевода как метку Prometheus.

## 9. Метрики и логи

Добавить Micrometer registry для Prometheus и открыть /actuator/prometheus только на внутреннем порту управления. Экспортировать стандартные метрики JVM, процесса и HTTP, а также минимум собственных метрик по двум видам бизнес-операций: просмотр баланса и перевод. Для собственных метрик нужны число запросов с исходом success, business_error или technical_error и длительность обработки. Клиентские тайм-ауты учитывает только внешний генератор нагрузки. Метки ограничить видом операции и исходом; не добавлять accountId, transferId или idempotencyKey.

Основной источник пользовательских SLI — внешний клиент/генератор нагрузки: серверная метрика не видит все случаи потери ответа или клиентского тайм-аута. Серверные метрики, события Pod и логи нужны для объяснения причин. Логи в stdout: время UTC, уровень, тип операции, ID экземпляра, код результата и время выполнения. Не выводить пароли и полный ключ идемпотентности.

Не вычислять в приложении научный итоговый балл R или K. Подготовить данные так, чтобы извне можно было получить N_all, N_ok, P95/P99, интервалы нарушения приемлемого обслуживания, число реплик, CPU и память.

## 10. Конфигурация и запуск

Локальная разработка на Windows: Java из IntelliJ IDEA или Maven Wrapper; существующий PostgreSQL пользователя. Параметры БД через переменные окружения BANK_DB_URL, BANK_DB_USER, BANK_DB_PASSWORD. Добавить .env.example без реального пароля и понятный README с созданием отдельной тестовой БД, запуском миграций при старте, командой запуска через mvnw.cmd и адресом http://localhost:8080/. Не требовать глобально установленный Maven, Docker Desktop или Node.js для первого локального запуска.

Контейнер: Dockerfile с воспроизводимой сборкой через Maven Wrapper и запуском JAR, без копирования локальных секретов. Собранный образ должен запускаться с переменными БД. Для Ubuntu Server/K3s добавить простые манифесты в k8s/: PostgreSQL с постоянным томом, bank-api Deployment, Service для HTTP API, отдельная конфигурация/секреты для тестовых учётных данных и HPA для нужного варианта. Не включать личные пароли в Git. Сборку образа на Ubuntu и импорт в хранилище образов K3s либо публикацию в реестр описать в README; выбрать один простой рабочий путь и проверить его. K3s использует containerd, поэтому наличие Docker-образа в Docker Engine само по себе ещё не делает его доступным Pod.

Сервис должен быть доступен из браузера на основном компьютере через адрес ноутбука в локальной сети (например, NodePort, если он выбран в манифестах). В README дать точный способ узнать адрес и проверить GET /api/accounts. На одном физическом ноутбуке допускаются проверки удаления Pod и отказа процесса; отказ самого узла не считать покрытым.

Для всех сравниваемых настроек фиксировать одну версию образа приложения и базы, одинаковые тестовые данные, параметры ресурсов, правила API и профиль нагрузки. Параметры Kubernetes допускается настраивать в манифестах, не переписывая Java-код.

## 11. Варианты конфигурации для будущего сравнения

Приложение само по себе одинаково во всех вариантах. Меняются только настройки Kubernetes. Подготовить четыре небольших файла или оверлея манифестов:

- V0: 1 реплика bank-api, без пользовательских readiness/liveness probes, без HPA.
- V1: 3 реплики, без пользовательских probes, без HPA.
- V2: 3 реплики, с одинаково настроенными readiness/liveness probes, без HPA.
- V3: те же начальные 3 реплики и probes, HPA по CPU с минимумом 3 и максимумом 5 реплик.

V0 соответствует варианту A текущего черновика статьи, V2 — B, V3 — C. V1 добавлен для возможности отделить эффект числа реплик от эффекта проверок; если он не используется, нельзя приписывать разницу A→B одному механизму. Даже V0 не означает «Kubernetes без восстановления»: Deployment и обычная политика перезапуска контейнера продолжают действовать.

Во всех вариантах оставить одинаковые CPU/memory requests и limits, одну версию образа и одну БД. Начальные значения для настройки можно выбрать после первого запуска и явно записать в манифестах; до сравнения зафиксировать их. Для HPA задать CPU request, иначе процент загрузки для масштабирования может быть неопределён. Выбор 3 и 5 реплик — рабочий параметр стенда, не результат исследования и не банковский норматив. На одном узле все реплики разделяют риск отказа узла.

## 12. Минимальные внешние сценарии и данные для исследования

Приложение должно позволять, без изменения исходного кода, наблюдать:

- Удаление выбранного Pod во время постоянного потока допустимых запросов. Сравнивать клиентский результат и время восстановления Pod отдельно.
- Моделируемую недоступность одного экземпляра через researchfault. Проверять, когда он перестал обслуживать API, когда был исключён из маршрутизации и когда вернулся.
- Всплеск нагрузки с одинаковым профилем для всех вариантов. Для HPA фиксировать время изменения числа реплик и пользовательские задержки до/после него.

Добавить короткие скрипты k6 в load/: smoke.js для проверки API, constant.js для постоянной нагрузки и spike.js для фиксированного всплеска. Профиль нагрузки, длительность, тайм-аут клиента, доля запросов баланса/перевода и адрес сервиса задаются параметрами скрипта. Начальные значения можно предложить, но не называть нормативом. Каждый новый перевод получает новый Idempotency-Key; повтор того же перевода — прежний. Нагрузочные запросы должны быть валидными и не опустошать один счёт: чередовать направления, выбирать небольшую сумму или явно сбрасывать тестовые данные между сериями.

Проверять ответы содержательно: для просмотра баланса — существующий счёт и неотрицательный баланс; для перевода — корректные ID/сумма/статус и возможность прочитать созданную запись. После серии отдельно проверить инвариант суммы балансов и отсутствие дубликатов ключей. Клиентский тайм-аут считать неуспешным для пользовательской метрики, но отдельно учитывать случаи, когда операция позже обнаружилась в БД. Не считать число запросов в одной серии числом независимых повторов исследования.

Не включать фиксированные «результаты эксперимента» в README, код или тестовые данные. Сохранять сырые данные и версии конфигурации, чтобы их можно было проанализировать позднее.

## 13. Проверки корректности и критерии приёмки

Перед сдачей реализации другой агент должен выполнить доступные проверки и сообщить фактические результаты, не выдавая непроверенное за готовое.

1. Проект собирается Maven Wrapper под Java 17 и запускается с PostgreSQL без Docker Desktop на Windows.
2. В браузере открывается одна страница; она получает счета, создаёт перевод, обновляет балансы и показывает историю.
3. Первый POST перевода меняет оба баланса ровно один раз; повтор с тем же ключом возвращает тот же перевод без списания; тот же ключ с другим телом даёт 409.
4. Отрицательная/нулевая сумма, перевод себе, недостаток средств и неизвестный счёт не меняют ни один баланс и не создают перевод.
5. Конкурентные переводы и конкурентные повторы одного ключа сохраняют инварианты БД: нет отрицательных балансов, двойного списания и потерянных обновлений. Добавить содержательные интеграционные тесты на отдельной тестовой PostgreSQL. Юнит-тесты не должны только повторять текст реализации.
6. После перезапуска Java-процесса/Pod данные и история сохраняются. Сброс выполняется только явным скриптом.
7. В обычном режиме нет публичного управляющего endpoint для отказов. В research-профиле можно адресно включить и автоматически снять моделируемую недоступность одного Pod.
8. На основном HTTP-порту работают /livez и /readyz; у V2/V3 пробы используют именно эти пути. При ошибке БД liveness не провоцирует массовые перезапуски.
9. /actuator/prometheus отдаёт метрики на внутреннем порту; k6 различает технический ответ, бизнес-ошибку и тайм-аут со стороны клиента.
10. На Ubuntu/K3s образ и манифесты поднимают приложение и PostgreSQL; API доступен по указанному в README адресу. HPA не считать проверенным, если нет метрик CPU или свободных ресурсов для новых Pod.
